** Decisions
*** [2026-05-21] – Use =patch-package= over a hand-rolled =postinstall= script
**** Reason
The fix requires modifying =node_modules/yargs/package.json= — a state that does
not survive =npm ci=.  A hand-rolled =postinstall= script (Node ESM file editing
the JSON in place) works but silently does nothing if upstream yargs ever changes
shape.  =patch-package= applies a checked-in diff and fails loudly when the target
file drifts, which is the desired behavior for a node_modules workaround.
**** Alternatives considered
- Hand-rolled script under =scripts/=: less robust, no drift detection.
- =npm overrides= to force yargs 16 (pure CJS): c8 pins =yargs: ^17.7.2=, so the
  override would violate the range and could break c8.
- Switch to Node's built-in =--experimental-test-coverage=: works for terminal
  output, but lacks an HTML reporter equivalent to =c8 --reporter=html=.

*** [2026-05-21] – Patch yargs's =package.json= (remove =type: module=) rather than the =yargs/yargs= file
**** Reason
On Node 26, =require('yargs/yargs')= from c8's CJS code triggers ESM loading of
=node_modules/yargs/yargs= (extensionless file) because the yargs package
declares =type: module=.  The file's content is CJS (=require=, =module.exports=)
— so Node throws =ReferenceError: require is not defined in ES module scope=.
Rewriting the file to ESM was attempted but breaks c8 differently: =require(esm)=
returns the namespace object =\{ default: Yargs \}=, not the function, so
=Yargs([])= fails with =TypeError: Yargs is not a function=.  Removing =type:
module= from yargs's =package.json= is the minimal change — Node then treats
extensionless files as CJS by default, which matches their actual syntax.
The =.mjs= files in yargs keep working because their extension is explicit.
**** Alternatives considered
- Rewrite =yargs/yargs= to use =import=/=export default=: breaks the CJS consumer
  (c8) because of the =require(esm)= namespace-wrapping behavior.
- Rename =yargs/yargs= to =yargs.cjs= and update exports: requires patching two
  files instead of one.

*** [2026-05-21] – Pass =--exclude '^$'= when creating the patch
**** Reason
=patch-package=' default =--exclude= regexp is =package\.json$=, so by default
changes to =package.json= are silently dropped from generated patches.  Since
our entire fix lives in =yargs/package.json=, the exclusion has to be overridden
at creation time.  This flag is only needed when /generating/ the patch; applying
it at =postinstall= time works without any flag.

* DONE Friendly `parseArgs` error reporting and test helper cleanup
Fix raw stack traces on bad CLI args; clean up test helpers; remove noisy ESLint rules.

** Decisions
*** [2026-04-17] – Catch `ERR_PARSE_ARGS_*` specifically; re-throw everything else
**** Reason
Node's `parseArgs` throws a `TypeError` with a `code` field starting with `ERR_PARSE_ARGS_`
for bad arg combinations (e.g. `--ref --force`). Without a handler this propagates as an
uncaught exception, dumping a full stack trace and a `Node.js vX.Y.Z` footer — making a user
error look like a bug. Catching only `ERR_PARSE_ARGS_*` codes (re-throwing others) prints
one clean `Error:` line and exits 1, consistent with the existing `console.error` +
`process.exit(1)` pattern elsewhere in `parse_args()`.
**** Alternatives considered
- Catch all errors from `parseArgs`: would swallow genuine bugs.

*** [2026-04-17] – Remove `complexity`, `max-statements`, `max-params` ESLint rules
**** Reason
All three rules fired on every large function in the codebase — parsers, workflow
orchestrators, CLI dispatch — without catching real problems.  Warnings that fire constantly
train developers to ignore lint output.  Bumping thresholds to one above the current
worst offender carries no semantic meaning and will be violated again as code grows.  Inline
`eslint-disable` per function scatters suppression noise through source.  Removal is the right
call for rules that don't fit the codebase.
**** Alternatives considered
- Bump thresholds: arbitrary numbers, will be violated again.
- Inline `eslint-disable` per function: noise in source, doesn't fix the root cause.

*** [2026-04-17] – `run_script(...args)` as the single public generic test helper; private `exec_script(args, options)` for internal use
**** Reason
`run_help` and `run_cli` were identical — one redundant name eliminated.  The shared
try/catch pattern across all four helpers extracted into private `exec_script(args, options?)`.
Public `run_script` uses rest params so test call sites read naturally
(`run_script('deploy', '--bogus')`).  `run_init` and `run_deploy` call `exec_script` directly
to pass custom `env`/`cwd` without exposing those options on the public API.
Simplified catch blocks: removed defensive `?? ''` fallbacks redundant given `exec_file`'s
known error shape.  `run_deploy` now calls `git_commit` instead of duplicating the two git
commands inline.
**** Alternatives considered
- Array call style for `run_script`: consistent with `exec_script` signature but less readable
  at test call sites.

A warning on their existence would be paternalistic.  Keeping the check to =.source.md= files
is honest: that's where an unclosed comment provably corrupts the deploy output (the rest of
the file is stripped).  Bonus: simplifies =check_no_unclosed_comments= — no need to call
=strip_html_comments= for plain =.md= entries.
**** Alternatives considered
- Error for =.md= too: contradicts "error = tool's own transform is broken"; =.md= deploys as written.
- Warning for =.md= (existence of any comment): too many false positives; HTML comments in
  =.md= are intentional in real skills.
- Warning for unclosed comment only in =.md=: still a false positive risk; renderer behavior
  is undefined and not skill-shed's responsibility.

*** [2026-04-21] – Two severity tiers: errors and warnings
**** Reason
Three tiers (errors / warnings / slow checks) were considered but rejected: the third tier
describes mechanism (network I/O), not severity, making naming misleading.  Two tiers with
an opt-in flag for expensive checks is cleaner.  Boundary rule: /error = deploy would
produce broken or undeployable output; warning = deploy succeeds but output may be
suboptimal or non-conforming/.
**** Alternatives considered
- Three tiers (errors/warnings/slow): naming the third tier on a severity axis is
  dishonest — a broken URL is not less severe than a duplicate heading.

*** [2026-04-21] – =lint= runs errors + warnings; =--check-urls= opts in to URL checking
**** Reason
URL checks are slow and network-dependent.  Opt-in (=--check-urls=) avoids surprising users
with slow or flaky lint runs.  =lint= without the flag is always fast and works offline.
=deploy= does not accept =--check-urls= at all — silently ignoring a flag would be
confusing.
**** Alternatives considered
- Opt-out (=--no-network=) on =lint=: constant paper cut for users without network; opt-in
  is safer.

*** [2026-04-21] – =deploy= runs only error checks, silences warnings
**** Reason
Deploy is a mechanical operation; style opinions should not abort it.  Silencing warnings
entirely is simpler to implement (warning code path never runs) and keeps deploy output
stable for scripting.
**** Alternatives considered
- Print warnings but don't abort: clutters deploy output; warnings would need to run anyway.

*** [2026-04-21] – =lint= accepts same source-mode flags as =deploy= (=--clean=, =--workdir=, =--ref=)
**** Reason
Manifest-building functions already exist and are parameterized by source mode.  Lint
operates on the same manifest entries, so the flags come for free.  Default is =--clean=,
mirroring deploy.

*** [2026-04-21] – Output format: =file:line: error: message= / =file:line: warning: message=
**** Reason
Standard compiler/linter format; parsed natively by editors and CI tools.  Deploy and lint
share the identical format — deploy simply never emits =warning:= lines.  All output goes
to stdout.
**** Alternatives considered
- Errors to stderr, warnings to stdout: complicates piping and scripting.

*** [2026-04-21] – Exit codes: 1 on any error, 0 on warnings-only or clean
**** Reason
Standard convention.  Exit 0 on warnings means lint can be used in CI without being
over-strict about style issues.  Exit 2 reserved for tool-level failures (unreadable file,
bad invocation) if needed later.

*** [2026-04-21] – Invalid URL is a warning, not an error
**** Reason
A URL that returns 4xx/5xx does not make the skill undeployable — it is a content quality
issue.  Treating it as an error would block deployment over a temporarily unavailable
external resource.  401/403 gets a distinct message ("may require authentication or be
invalid") to give actionable information.
**** Alternatives considered
- Invalid URL as error: too strict; transient failures or auth-gated URLs would block deploy.

*** [2026-04-21] – URL checks run in parallel with no concurrency limit
**** Reason
A single skill realistically has a handful of URLs.  Full parallelism is simpler and fast
enough; rate-limiting or host saturation is not a realistic concern at this scale.

*** [2026-04-21] – Unclosed fenced code block is an error for both =.source.md= and =.md= files
**** Reason
A file with an unclosed fence renders incorrectly regardless of whether comment stripping
is involved — the deployed skill is broken either way.  Uniform treatment is simpler to
document and implement; a per-file-type distinction would be surprising.
**** Alternatives considered
- Warning for =.md=, error for =.source.md=: too subtle; an unclosed fence is always broken
  output from the reader's perspective.

*** [2026-04-22] – No external Markdown parser/linter dependency for structural checks
**** Reason
A dedicated parser (e.g. =markdownlint=, =remark=) would subsume unclosed fences, empty
sections, and duplicate headings, but: (1) adding a dependency requires explicit approval
(project policy); (2) external linters report in their own format and don't integrate
cleanly with skill-shed's =file:line: error: message= model; (3) they cover only a small
fraction of the lint feature — frontmatter validation, unreferenced files, and comment
checks still require custom code regardless.  The hand-rolled state machine is a small
delta on top of logic already present in =strip_html_comments=.
**** Alternatives considered
- =markdownlint= / =remark=: correct and comprehensive for Markdown structure, but
  dependency cost outweighs benefit given how little of the lint feature they would cover.

*** [2026-04-21] – Unclosed-fence check runs on target content; uses line map for source line reporting
**** Reason
Checking target content (post-stripping) is correct by construction: a fence opener inside
a stripped comment block is itself commented out and never appears in the deployed file, so
not flagging it is correct behavior, not a silent miss.  The existing line map translates
target line numbers back to source line numbers for =.source.md= files; plain =.md= files
need no map since target = source.

*** [2026-04-21] – Fence-tracking logic duplicated (with link comments) rather than abstracted
**** Reason
Exactly two call sites (=strip_html_comments= and the lint fence checker), trivial state
machine, solo project.  A factory-function abstraction would be over-engineered for this
scope.  Link comments make the duplication intentional and auditable.  If fence handling
grows beyond ~10 lines or a third call site appears, extract the abstraction then.
**** Alternatives considered
- =make_fence_tracker()= factory function returning a =feed(line)= closure: correct
  approach if complexity grows, but premature for two stable call sites.

*** [2026-04-21] – Warn on skill directory files not reachable from =SKILL.md= via BFS
**** Reason
Unreferenced files are a useful signal for three real problems: (1) a filename typo in
=SKILL.md= (the most important case — the referenced file appears missing and the actual
file appears unreferenced); (2) stale files left over from a previous version of the
skill; (3) files that should be in =.gitignore=.  Warning message is plain "file not
referenced in SKILL.md" — no special-casing for =~= files or =.gitignore= suggestions,
to avoid coupling the linter to git assumptions.

A flat "search all files for each filename" approach was considered but rejected: two
mutually-referencing orphaned files would each be found in the other and neither would be
flagged.  BFS traversal from =SKILL.md= closes this gap with minimal extra complexity.
Reference detection uses substring search (filename only, not full path) rather than
Markdown link parsing, so references in prose, code blocks, and shell commands are all
covered.

Algorithm:
#+begin_src
visited   = {}
unvisited = {all files in skill directory} \ {SKILL.md}
queue     = [SKILL.md]

while queue is non-empty:
    file = dequeue(queue)
    content = read(file)
    visited.add(file)
    for each f in unvisited:
        if f.name appears in content:
            unvisited.remove(f)
            queue.enqueue(f)

warn for each file remaining in unvisited
#+end_src

Known limitation: two files with the same name in different subdirectories could produce
a false negative, but this is an unlikely edge case in a skill directory.

*** [2026-04-21] – No file-existence check for paths in fenced-block info strings
**** Reason
Skills commonly contain template paths and placeholder examples (e.g. =src/your-file.ts=,
=path/to/file.js=) in fenced block info strings.  There is no reliable way to distinguish
a real file reference from an example, so false-positive rate is too high to be useful.
A missing file would be caught at runtime anyway.
**** Alternatives considered
- Check only paths that exist somewhere in the skill directory: still fragile.
- Opt-in =--check-files= flag: low value for the implementation cost.

*** [2026-04-21] – Frontmatter validation: dedicated functions with error/warning severity
**** Reason
Frontmatter validation is encapsulated in two functions so the lint orchestrator does not
embed knowledge of valid fields or values.  The URL comment is the authoritative source.
Per-field validation depth varies: full validation for fields with enumerable or
regex-testable values (=name=, =user-invocable=, =disable-model-invocation=, =effort=,
=context=, =shell=); partial validation for complex fields (=allowed-tools=: check format
only, flag unknown tool names as warnings).  Cross-field checks (e.g. combined
=description= + =when_to_use= length > 1536 characters) cannot be expressed per-field and
live in the top-level function.  Return type carries severity so warnings and errors are
distinguished.

**** Reason
skill-shed is a portable tool — the same skill may be deployed to Claude Code, Cursor, or
any future Agent Skills-compatible tool.  Each tool may define its own frontmatter

**** Alternatives considered
- Validate union of agentskills.io + Claude Code fields: ties skill-shed to Claude Code,

- Warn on all non-spec fields: same problem, plus noisy for every Claude-specific field.

*** [2026-04-21] – Warn on unknown fields with Levenshtein distance ≤ 2 from a known field (typo detection)
**** Reason
Accepting unknown fields silently means typos (=desciption=, =naem=) pass undetected.
Fuzzy-matching against the known portable field names catches likely typos without
penalizing legitimate extensions — a field two edits away from =description= is almost
certainly a mistake.
**** Alternatives considered
- Warn on all unknown fields: penalizes tool-specific extensions; rejected above.
- Exact-match only: silently accepts typos; user gets no feedback on likely mistakes.

**** Alternatives considered
- =is_known_frontmatter_key= + =validate_frontmatter_value= as two separate functions:
  rejected — unknown key is just one possible error; a single function handles both in
  sequence and callers only need one call.
- =string | null= return type: insufficient once warnings are needed alongside errors.

*** [2026-04-21] – =description= length > 1024 characters is an error; body > 20000 characters is a warning
**** Reason
The agentskills.io spec sets a hard 1024-character limit on =description= — exceeding it
is a spec violation and an error.  The spec recommends keeping the =SKILL.md= body under
5000 tokens (see https://agentskills.io/specification#progressive-disclosure); this is a
soft recommendation, so a warning is appropriate.  A real tokenizer is not needed: the
4 characters/token approximation is well-known and sufficient for a lint hint.  Warning
message must state the approximation explicitly so authors understand the figure is not
exact, e.g. "body is approximately N tokens (4 chars/token approximation) — the
agentskills.io spec recommends keeping it under 5000 tokens".

*** [2026-04-21] – No line length check
**** Reason
Line length is an author preference, not a correctness concern.  Soft-wrapping workflows
(e.g. Emacs) and most Markdown renderers handle long lines gracefully.  The agentskills.io
spec imposes no line length constraint.  A warning that fires on organically-written
paragraphs trains authors to ignore lint output.

array methods, breaking =toSorted= and cascading into implicit-=any= errors throughout the
file.  Switched to =lib: ["ES2024"]= so both checkers agree.  =RegExp.escape= (Stage 3 proposal,
not yet in any TS lib) is suppressed with a single =@ts-expect-error=.
**** Alternatives considered
- Replace =toSorted= with =[...arr].sort=: works, but loses the cleaner idiom and doesn't fix
  the root cause (invalid =lib= value still accepted silently by =tsgo=).

*** [2026-04-10] – Use stage > 0 entries to detect index conflicts; abort =--staged= with generic "conflicts" message
**** Reason
During merge, rebase, cherry-pick, revert, and =git am=, git writes stage-1/2/3 entries to the
index for conflicted files instead of a single stage-0 entry.  Checking for any stage > 0 entry
(from the =git ls-files --stage= output already being read) detects all conflict-producing operations
without enumerating =.git/= sentinel files (=MERGE_HEAD=, =rebase-merge/=, etc.).  The check is
naturally scoped to =skill_dir= via the existing pathspec, avoiding false positives in monorepos
where a conflict exists in an unrelated subtree.  Error message says "conflicts" (not "merge conflicts")
since the cause may be any git operation.
**** Alternatives considered
- Detect in-progress state via =.git/MERGE_HEAD=, =rebase-merge/= etc.: requires maintaining a
  complete enumeration of sentinel paths; is repo-wide (false positives in monorepos); misses future
  git operations that produce conflicts.

*** [2026-04-02] – =--clean= cleanliness check scoped to =skill_dir= subtree, not the whole repo
**** Reason
=git status --porcelain -- .= (run with =cwd: skill_dir=) reports only staged, unstaged, and
untracked non-ignored files within =skill_dir=.  Dirty state elsewhere in a monorepo is irrelevant
to the deployed output, which is derived entirely from =skill_dir=.  Whole-repo cleanliness is
often impractical (in-progress work in sibling packages, editor swap files, etc.), so scoping to
=skill_dir= makes =--clean= usable in real monorepo workflows.
The only limitation — indirect dependencies on dirty state outside =skill_dir= (e.g. generated
files) — is a user-responsibility issue: =skill_dir= should be self-contained by design.
**** Alternatives considered
- Check whole-repo cleanliness (=git status --porcelain= without pathspec): rejected — impractical
  in monorepos; dirty state in other packages has no effect on the deployed output.

*** [2026-04-01] – Use =let manifest: Manifest = []= + explicit else guard; remove =!= assertions

  an empty manifest.
- =let manifest: Manifest | undefined= + explicit guard after the branch: valid, but adds an extra

*** [2026-03-31] – Two-tier dispatch: MANIFEST_COMMAND → git (no filesystem fallback tier)

*** [2026-03-30] – Atomicity: sentinel file approach; no write-to-temp-then-rename
**** Reason
A crash mid-write-loop leaves some target files at new content and some at old,
with the sidecar still recording old hashes — spurious hash-mismatch error on
next deploy.  Fix: write a ~.skill-shed-deploy-in-progress~ sentinel at the
start of the write loop, delete it after ~write_sidecar~.  On next deploy,
~deploy()~ checks for the sentinel before the overwrite check; if present, exits
with code 1 telling the user to re-run with ~--force~.
Disk-full failures are considered negligible (skills are small).
Write-to-temp-then-rename (atomic sidecar write) was considered but rejected:
it only fixes the case where all file writes succeeded but the sidecar write
itself was interrupted — a much narrower fix that still leaves the mid-loop
crash unaddressed.
**** Alternatives considered
- Ignore entirely, rely on ~--force~ for recovery: confusing error message gives
  no hint that interrupted deploy is the cause.
- Write sidecar first, then files: still produces mismatches (new hashes, old
  file content after crash).
- Write to temp then rename (atomic sidecar): only fixes torn-sidecar-write,
  not mid-loop crash.
- Write all files to a temp directory, then rename the whole directory into
  place: truly atomic, but ~rename~ across directories is not atomic on all
  filesystems, and replacing a live target directory atomically requires
  platform-specific tricks (~renameat2~ on Linux, not available in Node's
  ~fs.rename~).  Significant complexity for a tool that deploys small text files.
- Per-file write-to-temp-then-rename: atomic per file, but does not help if
  the process crashes between files; target still ends up in a mixed state.
  More code, same fundamental problem.
- Revert partially successful deploy on next run: save the previous content of
  each target file before overwriting, then restore on interrupted-deploy
  detection.  Truly recovers the pre-deploy state, but requires storing backups
  of all target files (doubling storage), significantly more code, and adds a
  new failure mode (crash during the revert itself).  Overkill for small text
  files where re-deploying with ~--force~ is trivially fast.

*** [2026-03-26] – Manifest is an array of ManifestEntry objects, not a Map
**** Reason
Iteration is the dominant operation; lookup by name is rare and only needed
for ~5–20 entries (skill files are small).  The conflict check
(~SKILL.md~ vs ~SKILL.source.md~ both resolving to the same target) requires
an explicit scan regardless of container — a ~Map~ keyed by target name would
silently overwrite and still needs a pre-check.  Since the ~Map~ invariant
doesn't help here, an array is the more honest representation: an ordered
collection of records with no artificial primary key.  A ~validate_manifest~
function checks for duplicate ~target_name~s explicitly, replacing the
implicit (but non-functional) ~Map~ guarantee.
**** Alternatives considered
- ~Map<string, ManifestEntry>~ keyed by ~target_name~: doesn't enforce
  uniqueness for the source-conflict case; O(1) lookup irrelevant at n ≤ 20.

*** [2026-03-26] – ManifestEntry shape: source_name, target_name, source_content, target_content, line_map
**** Reason
All transform types (comment stripping, Org→md, AsciiDoc→md) produce a
source and a target.  Storing both in one entry gives linting access to
the source and deploy access to the target without reconstruction.
~source_content~ is ~string | Buffer~ (string for ~.md~/~.source.md~,
Buffer for ~.org~ etc.); ~target_content~ is always ~string~ (always ~.md~
after any transform).  ~line_map~ is optional: only meaningful when
~source_content~ is a string (comment-stripping path); undefined for
pandoc-converted sources.  Pass-through files have
~source_name === target_name~ and ~source_content === target_content~.
**** Alternatives considered
- Store only ~target_content~: loses source for linting and line mapping.
- Store ~source_content~ only for transformed files: inconsistent shape,
  complicates consumers.

*** [2026-03-26] – Manifest stores .md files as strings, all others as Buffers
**** Reason
~Buffer → string~ via UTF-8 is not lossless for binary files (invalid byte
sequences are replaced with U+FFFD), so storing binary files as strings is
wrong.  A null-byte heuristic for binary detection is unreliable and puts
content-type logic in the wrong layer.  Extension-based detection is
deterministic and correct: ~*.md~ files (including ~*.source.md~) are always
text; everything else is kept as ~Buffer~.  No heuristic needed; the manifest
already has the filename.
**** Alternatives considered
- ~Buffer~ for all files, decode at use site: scatters ~.toString('utf8')~ calls
  across all consumers; punishes the common (text) case.
- Null-byte heuristic: unreliable; misclassifies valid UTF-8 with embedded nulls.
- ~string~ for all files via ~latin1~: technically lossless but unnatural and
  requires ~latin1~ encode/decode at every binary use site.

*** [2026-03-25] – Replace mtime guard with content-hash sidecar `.skill-shed-manifest.json`
**** Reason
Mtime is unreliable in a git workflow: index objects have no mtime; `git
checkout`/`stash pop` reset working-tree mtimes to now; partially staged
files have a working-tree mtime that differs from the staged content.
Content hashing is immune to all of these.  The sidecar records SHA-256
hashes of every file as deployed; next deploy compares current target
hashes against stored hashes to detect direct edits.
**** Alternatives considered
- Keep mtime for single-file and add hashing only for multi-file: two code
  paths, inconsistent semantics.

*** [2026-03-25] – Sidecar `.skill-shed-manifest.json` lives in the target directory
**** Reason
The sidecar guards the target, so it belongs there.  The overwrite check
can be performed without knowing the source path or loading ~.env~.  If
the source directory is moved or deleted the target remains protected.
**** Alternatives considered
- Source dir: requires resolving target path before the check can run;
  orphaned if source dir is moved.

*** [2026-03-25] – Per-file overwrite safety check against sidecar
**** Reason
For each file to be deployed, three cases arise:
1. Target file absent: write freely (genuinely new).
2. Target file present, sidecar has entry: hash check — abort if hashes
   differ (direct edit detected), otherwise overwrite.
3. Target file present, sidecar has no entry (sidecar absent or file not
   listed): abort unless ~--force~ (file may have been manually created).
The deploy aborts as a whole on any case-2 or case-3 hit; partial deploys
leave the target in an inconsistent state.  ~--force~ bypasses both the
missing-sidecar check and a hash-mismatch check (same flag, same
semantics: "I accept responsibility for any overwritten edits").
**** Alternatives considered
- Abort only when sidecar is entirely absent: misses the case where a new
  file is added to an existing multi-file skill after first deploy.
- Abort only the conflicting file, deploy the rest: partial deploy leaves
  target inconsistent; --force covers the intentional-overwrite use case.

*** [2026-03-25] – Stale-file policy: delete owned files, abort on unowned files
**** Reason
A file present in the target but absent from the current deploy set falls
into one of two cases, distinguishable via the sidecar:
- In sidecar: skill-shed deployed it; it was deleted in the new version.
  Safe to auto-delete.
- Not in sidecar: not deployed by skill-shed; origin unknown.  Abort
  unless ~--force~ (conservative; may warrant further thought).
**** Alternatives considered
- Warn instead of abort on unowned files: leaves target in mixed state,
  harder to reason about.
- Ignore unowned files: silently accumulates cruft.
